# 공개 Jira 이력 벤치마크

**[English](BENCHMARK.md) | 한국어**

H1~H5는 데모 프로젝트 세 개로 측정합니다. 이것이 타당성의 가장 큰 위협이라고 우리 [검증 가이드](PAPER_VALIDATION_GUIDE.ko.md)에도
적혀 있습니다. 로드맵 3([#38](https://github.com/ma-pmo/ma-pmo-ext/issues/38))은 공개 Jira의 실제 릴리스 이력을
재생해, 리스크·일정 에이전트를 실제로 일어난 일과 대조합니다. 이 문서는 그 첫 단계인 "그럴 만큼 이력이 충분한가"를
다룹니다.

## 데이터

[Public Jira Dataset](https://arxiv.org/abs/2201.08368)(Montgomery, Lüders, Maalej, MSR 2022)의 익명화된 2025-06-23판
([Zenodo](https://zenodo.org/records/15719919), CC BY 4.0). 공개 Jira 16곳(Apache, Red Hat, Jira, Mojang, Spring, Qt,
MariaDB, Hyperledger, MongoDB, Sakai, Second Life, JFrog, Sonatype, Intel DAOS, Mindville, Jira Ecosystem)의 이슈 필드와
변경 이력 전체가 들어 있습니다. 5.8GB zip 하나에 `mongodump --gzip --archive` 파일이 있습니다(MongoDB에 풀면 약 60GB).

데이터는 이 저장소에 넣지 않습니다. 직접 받아 해시를 확인하세요.

```bash
curl -L -o ThePublicJiraDataset.zip \
  "https://zenodo.org/records/15719919/files/2025-06-23%20ThePublicJiraDataset.zip?download=1"
md5 ThePublicJiraDataset.zip        # 02f85309d966092ea130ca0797aea795
```

MongoDB는 필요 없습니다. `ma_pmo.benchmark.dump`가 zip 안의 아카이브를 스트림으로 읽습니다.

## 규칙

- **단위:** 릴리스. 출시되었고(released) 출시일이 있는 Jira fix version입니다.
- **시점:** T = 출시일 − k일(k = 14, 28).
- **T에 예정됨:** T에 이미 있었고, T에 미해결이었고, T에 그 릴리스가 fix version이었던 이슈. T의 fix version은 지금의
  fix version에서 T 이후의 "Fix Version" 변경을 모두 되돌린 것입니다.
- **결과:** 출시일 다음 날(D)에 봅니다.

  | 결과 | D 시점 | 레이블 |
  |---|---|---|
  | 제때 | 해결됨, 릴리스가 여전히 fix version | 안 밀림 |
  | 빠짐 | 릴리스가 더는 fix version이 아님 | 밀림 |
  | 미해결 | 릴리스가 fix version, 미해결, 이후에도 그 버전으로는 해결 안 됨 | 밀림 |
  | 늦음 | 릴리스가 fix version, 미해결, 나중에 버전을 유지한 채 해결 | 제외 |

  *늦음*은 레이블에서 뺍니다. 출시 뒤 QA나 정리 작업으로 닫는 경우가 많아(Jira 자체 트래커는 절반이 일주일 안,
  Apache는 몇 달 뒤) 릴리스에 들어갔는지 분명하지 않기 때문입니다.
- **T에 시작됨:** T 시점의 상태(fix version처럼 되돌려 구함)가 Open, To Do, Backlog 같은 시작 전 상태가 아님.
  시작된 이슈만 본 결과를 두 번째 집합으로 냅니다. 버전만 붙어 있던 백로그가 빠집니다.
- **쓸 수 있는 릴리스:** T에 예정되고 레이블이 있는 이슈가 20개 이상.
- **진행 기준:** 쓸 수 있는 릴리스 200개 이상, 그중 10개 이상인 인스턴스가 3곳 이상.

```bash
pip install "ma-pmo[benchmark]"
ma-pmo benchmark coverage ThePublicJiraDataset.zip            # Markdown
ma-pmo benchmark coverage ThePublicJiraDataset.zip --json     # 모든 카운터
```

## 릴리스 재생(2단계)

```bash
ma-pmo benchmark prepare ThePublicJiraDataset.zip --out bench-data   # 한 번만. 저장소에 넣지 않음
ma-pmo benchmark replay bench-data                                   # 릴리스 목록
ma-pmo benchmark replay bench-data Apache/12345678 --k 14            # 시점 T의 릴리스 하나
```

`prepare`는 쓸 수 있는 릴리스와 그 이슈들의 전체 이력을 남깁니다(`releases.jsonl`, `issues.jsonl.gz`,
`manifest.json`). **ReplayTracker**(`ma_pmo/benchmark/replay.py`)는 이를 보통 트래커 계약으로 내주므로, 실제
에이전트가 T 시점의 릴리스 위에서 그대로 돕니다. 릴리스 하나가 프로젝트 하나이고, T에 그 릴리스가 fix version이던
이슈가 태스크입니다(T에 해결됐으면 진척 100, 시작됐으면 50, 아니면 0. T의 원래 추정치, 없으면 8시간. T에 같은
릴리스 안에서 막고 있던 이슈가 의존 관계). 마감은 출시일이고, 태스크마다 T의 상태·우선순위·담당자·유형이 붙습니다.
모든 값은 지금 값에서 T 이후의 변경을 되돌린 것입니다. 테스트가 모든 이슈에 T 이후의 무작위 변경(상태, 해결,
우선순위, 담당자, 추정치, 링크, fix version)을 더해도 트래커가 똑같이 보이는지 확인합니다. 결과는 채점할 때만
읽고(`ReplayTracker.outcomes`) 에이전트에게는 보여 주지 않습니다. 결과물을 프로젝트에 묶어 저장하는 에이전트(A4는
경보를 `risk` 테이블에 남김)는 그 프로젝트가 DB에 있어야 하는데 재생 릴리스는 DB에 없습니다. 그래서 벤치마크는
A4를 신호 분석(`a4_signals`)으로 읽고, 재생 위에서 에이전트 전체를 돌리려면 일회용 DB가 필요합니다.

## 이슈 채점(3단계)

```bash
ma-pmo benchmark run bench-data              # Markdown. --json, --out results.json, --k 14 28
```

쓸 수 있는 릴리스에 T 시점에 예정된 이슈 하나가 한 행입니다. 밀렸으면(빠졌거나 출시 다음 날까지 미해결) 1, 제때
해결됐으면 0이고, 늦은 종료는 뺍니다. "T에 미해결"과 "출시까지 해결"은 해결 필드의 변경 이력으로 판단하므로, T
전에 해결됐다가 나중에 다시 열린 이슈는 T에 열린 것으로 세지 않습니다.

| 채점기 | T에 보는 것 |
|---|---|
| `all_slip` | 없음. 모두 밀린다고 봄(다수 클래스) |
| `progress` | 시작 전 1, 시작됨 0.5, 리뷰 중 0.2 |
| `a4_signals` | 재생한 릴리스에 A4 자신의 규칙 신호를 태스크별로 적용: 막힘 0.9, 정체 0.7, 그 외 0.3 |
| `forest` | 이슈 지연 연구의 특징(`benchmark/features.py`)으로 만든 랜덤 포레스트: 상태, 나이, 마지막 상태 변경 후 경과일, 지금까지 일정 변경 횟수, 링크, 우선순위, 유형, 담당자 부하, 릴리스 크기 |

릴리스를 날짜로 나눠 앞의 70%로 포레스트를 학습하고, 모든 채점기를 뒤의 30%에서 잽니다. 지표는 PR-AUC(릴리스 단위
부트스트랩 95% 구간), ROC-AUC, 0.5 기준 F1, Brier, ECE, 반대 질문(어떤 이슈가 들어가나)의 PR-AUC이며, 전체·변별
가능한 릴리스·T에 시작된 이슈로 나눠 내고 컬렉션별 PR-AUC도 냅니다. 테스트가 모든 이슈에 T 이후 무작위 변경을 더해도
특징이 바뀌지 않는지 확인합니다.

전체 덤프 결과(`ma-pmo benchmark run`, 시험 집합 = k = 14에서 가장 최근 릴리스 711개):

| 채점기 | 전체 이슈: PR-AUC [95% 구간] | ROC-AUC | ECE | 시작된 이슈: PR-AUC | ROC-AUC |
|---|---|---|---|---|---|
| all_slip | 0.829 [0.814, 0.843] | 0.5 | 0.171 | 0.620 | 0.5 |
| progress | 0.884 [0.869, 0.896] | 0.678 | 0.115 | 0.637 | 0.534 |
| a4_signals | 0.881 [0.866, 0.894] | 0.670 | 0.223 | 0.621 | 0.500 |
| forest | **0.964** [0.957, 0.970] | **0.858** | 0.039 | **0.869** | **0.793** |

k = 28에서도 순서는 같습니다(포레스트 PR-AUC 0.934, ROC-AUC 0.825. 시작된 이슈에서는 0.846, 0.804).

- **A4 규칙 신호는 "아직 시작 안 함"보다 나은 게 없습니다**(ROC-AUC 0.67 대 0.68). 이미 시작된 이슈에서는 우연
  수준입니다. 그런 이슈는 진척 50%라 "정체"로 잡히지 않고 릴리스 안에서 막히는 일도 드물어 모두 같은 점수를 받습니다.
- **문헌 기준선이 크게 앞섭니다.** 주로 이슈가 손대지 않은 채 지난 기간(마지막 상태 변경 후 경과일, 단독 ROC-AUC
  0.84)과 나이 덕분입니다. 오래되고 멈춘 이슈가 빠집니다. 에이전트가 넘어야 할 기준선입니다.
- **A4 점수는 보정돼 있지 않습니다**(ECE 0.22: "0.9"는 90%보다 훨씬 덜 밀리고 "0.3"은 훨씬 더 밀림). 로드맵 11이
  이 레이블로 보정합니다.

## 벤치마크에 주는 뜻

- **예정된 이슈 대부분이 밀리고, 대개는 버전에서 빠지는 방식입니다.** 출시 2주 전에 아직 열린 이슈의 46~88%가
  그 릴리스에 들어가지 못하고, 그 대부분은 릴리스에서 빠졌습니다. 변경 이력에 남은 계획 결정이라 깔끔한
  레이블입니다. "모두 밀린다"가 정확도로는 강한 기준선이므로 PR-AUC와 릴리스별 순위를 보고하고, 반대 질문("어떤
  이슈가 들어가나")도 함께 냅니다.
- **백로그가 비율을 부풀립니다.** 버전만 붙어 있던 이슈는 시작된 이슈보다 훨씬 자주 밀립니다(Jira 62% 대 22%,
  MongoDB 66% 대 44%). 시작된 이슈 집합을 함께 내서, 손대지 않은 백로그만 알아봐도 좋아 보이는 모델을 가려냅니다.
- **변별 가능한 릴리스가 주 평가 집합입니다.** 모든 이슈가 밀렸거나 하나도 안 밀린 릴리스는 가를 것이 거의 없습니다.
- **인과가 아니라 예측입니다.** 과거 기록에는 개입이 없어서, 이 벤치마크는 T 시점에 밀림을 내다볼 수 있었는지를
  재고, 경보가 밀림을 막았을지는 재지 않습니다.
- **한계.** `releaseDate`가 계획일이 아니라 실제 출시일일 수 있고, 변경 이력에 그 변경이 남지 않아, 이를 기준으로 한
  시점은 PM이 알던 것보다 조금 나중의 지식을 씁니다. 용량 데이터가 없어 H2는 다루지 않습니다. 오픈소스 프로젝트는
  기업 PMO가 아닙니다.

## 관련 연구

- Choetkiertikul 외, [Predicting delays in software projects using networked
  classification](https://seanalytics.github.io/papers/ASE2015-preprint-choetkiertikul-dam-tran-ghose.pdf)(ASE 2015),
  [Predicting the delay of issues with due dates](https://dx.doi.org/10.1007/s10664-016-9496-7)(EMSE 2017): Jira 프로젝트의

  릴리스 준비도를 이진 분류로 다룸.
