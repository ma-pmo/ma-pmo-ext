# 1. 에이전트는 왜 실패하나, 하네스란 무엇인가

**[English](01-why-harness.md) | 한국어** · [과정 지도](README.ko.md)

## 목표

조직에서 LLM 에이전트가 실패하는 방식을 구분하고, MA-PMO의 어느 부분이 각각을 잡아내는지 봅니다.

## 문제

에이전트 데모는 질문 하나에 한 번 잘 답합니다. 에이전트 *시스템*은 매일, 실제 데이터로, 다른
에이전트와 함께 돌고, 그 결과가 사람과 돈에 관한 결정을 바꿉니다. 이런 환경에서 망가지는 것은
모델보다 그 주변인 경우가 대부분입니다.

| 실패 | PMO에서 보이는 모습 |
|---|---|
| 자유 형식 출력 | 보고 에이전트가 "리스크: 대략 중간쯤"이라고 써서 다음 에이전트가 해석을 못 함 |
| 조용한 변화 | 프롬프트를 바꿨더니 리스크 경보가 줄었는데 한 달 동안 아무도 모름 |
| 장애 | 월요일에 API 키가 만료되어 주간 보고가 오지 않음 |
| 월권 | 확신도 0.41인 에이전트가 팀 배치를 바꿔 버림 |
| 검증 불가능한 주장 | "에이전트가 보고 시간을 줄였다" — 무엇과 비교해서, 어떻게 쟀는가? |
| 깨지기 쉬운 연동 | Slack 웹훅 주소가 틀려서 파이프라인 전체가 예외로 멈춤 |

## 하네스

**하네스**는 이런 실패를 드러나게 하거나, 범위를 가두거나, 아예 불가능하게 만드는 모델 주변의
엔지니어링입니다. MA-PMO에서는 여섯 부분으로 되어 있고, 남은 강의가 하나씩 다룹니다.

```
           목표 ─▶ A1 오케스트레이터 ─▶ A2…A7 작업자 ─▶ 종합 ─▶ 보고서
                     │      ▲              │
  계약 (2)      ─────┘      │              ├──▶ 감사 로그 (2)
  대체 경로 (3) ────────────┘              ├──▶ 승인 큐 (4)
  측정 (5)      ◀── KPI 계측 ◀─────────────┤
  실험 (6)      ── 시나리오 실행, 에이전트 제거
  연동 (7)      ◀── 이벤트 / 트래커 데이터 (장애 격리)
```

모든 부분에 던져 볼 질문: *이게 없다면 문제가 생긴 걸 어떻게 알아차릴까?* 답이 "사용자가 항의하면"
이라면 하네스에 빈틈이 있는 것입니다.

## MA-PMO에서는

- 에이전트: `ma_pmo/agents/` — A1 오케스트레이터, A2 계획(CPM), A3 자원, A4 리스크, A5 보고,
  A6 거버넌스(스테이지 게이트), A7 지식(출처를 단 과거 교훈).
- 실행: `ma_pmo/core/scenarios.py`가 시나리오를 계획 → 수행 → 완료 → 인사이트 4단계로 돌리며
  각 에이전트가 무엇을 냈고 얼마나 걸렸는지 기록합니다.

## 해보기

```bash
ma-pmo serve &                       # API :8000
curl -s -X POST 'localhost:8000/scenarios/quarterly_review/run?lang=ko' | python -m json.tool | head -60
```

출력에서 찾아보세요: A1이 어느 에이전트에 일을 맡겼는지, 각 결과의 스키마(`schedule.v1`,
`risk_alert.v1`, `report.v1`), 인사이트 단계의 KPI 기록.
