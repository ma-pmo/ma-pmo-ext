# LLM 비용

**[English](COSTS.md) | 한국어**

모든 LLM 호출은 비용 원장에 기록됩니다. 어느 실행의 어느 단계인지, 에이전트, 모델, 제공자가 알려 준 토큰,
그리고 USD 비용이 남습니다. LLM이 없는 에이전트나 API 키 없이 실행할 때는 결정론적 방식으로 동작하므로
비용이 들지 않습니다.

## 어디서 보나요

- 대시보드 → **비용**: 합계와 모델·에이전트·워크플로·날짜·실행별 비용. 최근 7·30·90일 또는 전체.
- `GET /costs?by=model|agent|workflow|run|day&days=30`: 같은 내용의 JSON.
- `GET /runs/{run_id}/costs`: 실행 하나의 단계별 비용.

다른 데이터처럼 원장도 워크스페이스별로 나뉩니다(Postgres에서는 행 수준 보안 적용).

## 예산

워크스페이스마다 예산 두 가지를 둘 수 있고, 각각 **경고 금액**과 **한도**(USD)가 있습니다.

| 예산 | 세는 대상 |
|---|---|
| `month` | 이번 달(UTC) 워크스페이스가 쓴 전체 비용 |
| `run` | 실행 1회가 쓴 비용 |

LLM을 호출하기 전마다 지금까지의 비용을 확인합니다.

- **경고 금액**을 넘으면 한 번 알립니다(로그와, 켜진 알림 연동으로 `budget.warning` 이벤트.
  `month`는 달마다 한 번, `run`은 실행마다 한 번). 아무것도 멈추지 않습니다.
- **한도**를 넘으면 호출하지 않습니다. 모든 에이전트는 호출이 실패하면 결정론적 방식으로 답하므로
  **실행은 끝까지 진행되어 성공합니다**. 실행에 그 이유가 남고(`GET /runs`의 `budget_fallback`,
  시나리오·목표 결과, 워크플로 화면의 표시), 비용 화면에 그런 실행 목록이 나옵니다.

한도를 넘기는 그 호출은 이미 이루어졌으므로, 한도는 최대 호출 1번만큼 넘을 수 있습니다. 가격 미상
호출은 세지 않습니다. 한도를 `0`으로 두면 LLM을 전혀 호출하지 않습니다.

비용 화면에서 정하거나 다음 명령을 씁니다.

```bash
ma-pmo budget set month --warn 40 --limit 50
ma-pmo budget set run --limit 0.50
ma-pmo budget show
ma-pmo budget clear run
```

`GET /budgets`는 예산과 이번 달 사용액을, `PUT /budgets/{month|run}`(`{"warn_usd": …, "limit_usd": …}`,
둘 다 `null`이면 삭제)은 예산을 바꾸며 `admin` 역할이 필요합니다.

## 단계별 모델 고르기

워크플로 단계에 `"model_tier": "fast"`를 주면 그 단계는 `LLM_MODEL` 대신 더 싼 `LLM_MODEL_FAST`를
씁니다(생략하거나 `"standard"`면 그대로). 워크플로 편집기의 **모델** 칸에서 고르거나 JSON에 적습니다.

```json
{"id": "report", "agent": "A5", "model_tier": "fast"}
```

다른 워크플로 변경과 똑같이 검증하고, 초안으로 저장하고, 게시합니다([docs/PLUGINS.ko.md](PLUGINS.ko.md)).
원장에 호출마다 쓴 모델이 남으므로 비용 화면의 모델별 표에서 효과를 볼 수 있습니다. 워크플로 단계 밖의
호출(목표 라우팅, `/knowledge/ask`)은 `LLM_MODEL`을 씁니다. `LLM_MODEL_FAST`가 비어 있으면 `fast`도
`LLM_MODEL`을 씁니다.

어느 단계에 빠른 모델을 써도 되는지는 가격만이 아니라 품질의 문제입니다. 아래의 재생 평가기가
워크플로를 바꾸기 전에 이를 측정합니다.

## 이 단계에 빠른 모델을 써도 될까? 재생해 보기

재생은 사용 중인 워크플로와, 단계 하나만 빠른 모델로 바꾼 워크플로를 각각 `N`번씩 번갈아 실행합니다.
임시 워크스페이스에서 데모 데이터로 실행하며, 그 단계에 대해 실행마다 다음을 비교합니다.

| 지표 | 의미 |
|---|---|
| 단계 비용 | 원장에 기록된 그 단계의 USD |
| 올바른 출력 비율 | 그 단계의 구조화 LLM 호출 중 대체 방식으로 넘어가지 않고 스키마에 맞는 답을 낸 비율(첫 시도 또는 재시도) |
| 리스크 판정 정확도 | 리스크 단계만: 리스크 경보의 심각도가 `ma_pmo/fixtures/risk_ground_truth.json`의 실제 결과와 맞는 비율 |

각 지표는 변화량과 95% 부트스트랩 신뢰구간으로 보고합니다. 판정은 다음과 같습니다.

- **추천**: 어떤 품질 지표도 허용치(기본 5%, 구간 하한)보다 더 떨어질 수 없고, 단계 비용이 줄어듦
  (구간 상한이 0보다 작음)
- **추천 안 함**: 그 밖의 경우, 이유와 함께
- **판단 불가**: 비교할 LLM 출력이 없음(API 키가 없거나 모든 호출이 대체 방식으로 처리됨)

저절로 바뀌는 것은 없습니다. `approver`가 추천된 변경을 승인하면 그 단계를 빠른 모델로 바꾼 워크플로
**초안**이 저장되고, 게시는 평소처럼 따로 합니다. 재생 이후 바뀐 워크플로의 추천은 승인할 수 없습니다.

```bash
ma-pmo replay risk_escalation A4 --repeat 5   # 표와 판정 출력
ma-pmo recommendation list
ma-pmo recommendation approve 1               # -> 초안 vN, 평소처럼 게시
```

비용 화면의 **모델 추천**이나 `POST /recommendations/replay`, `GET /recommendations`,
`POST /recommendations/{id}/approve|reject`로도 할 수 있습니다.

**비용과 한계.** LLM이 설정되어 있으면 재생은 실제로 호출합니다(실행 `2 × N`번). 그 비용은 이
워크스페이스의 원장에 남고(`purpose: replay`, `GET /costs?by=purpose`), 워크스페이스 예산이 적용됩니다.
데모 포트폴리오가 작아서 반복이 적으면 구간이 넓습니다. 구간을 확인하고, 좁아 보이는 결과를 믿기 전에
반복을 늘리세요. API 키가 없으면 모든 에이전트가 결정론적 방식으로 동작하므로 재생은 항상 판단 불가가
됩니다. 이것은 버그가 아니라 정직한 답입니다.

초안의 시험 실행도 같습니다. 그 비용이 남고(`purpose: dry_run`), 예산이 적용됩니다.

## 프롬프트 캐싱

Anthropic 모델에서는 시스템 프롬프트(에이전트 역할, 구조화 출력이면 JSON 스키마)를 캐시 가능으로 표시해,
반복 호출이 제공자 캐시에서 더 싼 가격으로 읽습니다. 제공자의 최소 길이보다 짧은 프롬프트는 캐시되지
않을 뿐입니다. 캐시 읽기와 쓰기는 원장에 따로 기록되고 따로 가격이 매겨집니다. `LLM_PROMPT_CACHE=false`로
끕니다.

## 가격

가격은 버전이 있는 가격표에서 가져오고, 원장의 각 행에 어느 가격표로 계산했는지 남습니다.

1. `MA_PMO_PRICE_TABLE`이 가리키는 직접 만든 JSON 파일
2. 없으면 설치된 LiteLLM에 포함된 가격표(버전이 `uv.lock`에 고정되어 있어, 업그레이드하면 변경이 드러남)

두 가격표 모두 모르는 모델은 **가격을 매기지 않습니다**. 그 호출은 "가격 미상 호출"로 따로 세고 USD
합계에서 빼며, 추정하지 않습니다. 로컬 모델(Ollama)은 LiteLLM이 0원으로 계산합니다.

직접 만드는 가격표는 100만 토큰당 USD입니다(`cache_read`, `cache_write`를 생략하면 `input`과 같음).

```json
{"version": "acme-2026-11",
 "models": {
   "anthropic/claude-sonnet-5": {"input": 3.0, "output": 15.0, "cache_read": 0.3, "cache_write": 3.75},
   "acme/in-house-model": {"input": 0.4, "output": 0.4}
 }}
```

모델은 적힌 이름 그대로 찾고, `provider/name` 형식이면 `name`으로도 찾습니다.

## 토큰 계산 방식

원장은 LiteLLM이 알려 주는 제공자 사용량을 그대로 둡니다. `prompt_tokens`에는 프롬프트 캐시에서 읽거나
캐시에 쓴 입력도 들어 있으며, 이 둘은 따로도 기록합니다(`cache_read_tokens`, `cache_write_tokens`).
가격 계산은 다음과 같습니다.

```
(prompt - 캐시 읽기 - 캐시 쓰기) × input + 캐시 읽기 × cache_read
  + 캐시 쓰기 × cache_write + completion × output
```

같은 응답에 대해 LiteLLM의 `completion_cost`와 결과가 같으며, 테스트가 캐시가 있는 경우와 없는 경우의
제공자 형식 사용량으로 이를 확인합니다. 재시도한 호출도 실제로 돈이 드므로 다시 셉니다. 기록이 실패해도
에이전트의 호출은 멈추지 않고 경고만 로그에 남습니다.
